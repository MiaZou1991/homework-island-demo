## 操作协议

由发起修改的设备保存修改前后的记录，生成独立 `operationId`、集合类型、记录 ID 和变更类型（`add / patch / remove`）。它记录一个业务操作，而不是整份旧家庭 JSON。

- **新增**：若记录 ID 不存在则追加；若已存在相同内容，按重试视为已经完成；若同 ID 不同内容，阻断并提示冲突。
- **编辑/完成**：逐字段比较“修改前／修改后”。云端此字段仍是原值才应用改动；云端已是目标值则认为该字段已完成；若云端被另一设备改成第三种值，阻断且不覆盖。可安全合并如“家长改作业内容、孩子标记完成”等非重叠修改。
- **删除**：只有云端整条记录仍与用户删除时看到的版本一致才删除；若其他设备修改了内容、携带物品等，阻断删除，避免丢失。
- **批次**：检测到冲突时返回已安全应用的候选状态供下一层处理，绝不直接替调用方写入服务端。调用者需要配合数据库 CAS，处理批量提交是否原子成功。
- 任何操作冲突都必须保留在 durable outbox 中，等待读回最新版本/用户明确决策；不允许在业务层直接覆盖。

## 从现有 `saveData()` 到操作队列：自动识别，不冒险忽略字段

`planTransition(beforePayload, afterPayload, operationIdFactory)` 负责在**真正发出网络请求前**比对本机前后状态：

- 为四类集合中具有稳定 `id` 的新增／修改／删除生成对应操作；不修改传入对象，不读取生产数据库。
- 对积分 `points`、完成总数 `totalCompleted`、成长及伙伴历史 `demoGrowth` 等其他顶层字段，只报告哪些字段发生了变化，返回 `safe:false`，**不能只上传作业部分并悄悄丢掉这些联动状态**。
- 数据集合整块丢失、原数组出现重复记录 ID、顺序变化但没有表示顺序的操作等情况一律报错或 `safe:false`；未来 UI 必须说明待同步状态，而不是展示“云端已同步”。
- 需要用户/开发者明确决定旧版积分等跨集合联动如何处理后，才能把 `safe:false` 接入后端事务；不能靠前端简单累加解决幂等性。
- 新旧设备之间只有相同业务记录的不同字段才允许自动合并；同一字段改动、删除与编辑竞争必须保留待处理操作。

## 安全接入的前置条件

1. **先身份**：服务端真实核实家庭成员。家长账号必须可恢复，孩子设备通过有效期有限的一次性邀请绑定；不能单靠前端固定 `KAIXIN` 或任何客户端可读家庭码授权。测试库中的匿名 JWT 不得直接当成长期家长账号。
2. **再持久化**：先保存完整操作（包括 base/next）到设备的 IndexedDB，然后更新本机可见状态与开始上传；如写入本机队列失败必须明确提示，不能假装“已同步”。
3. **再提交**：读服务端 revision，按本模块 `apply` 计算合并后的完整 payload，将 `expected_revision` + `operationId` 交给已验收的 `family_save_v2`。遇到 CAS 冲突重新读取并计算；同字段冲突保留队列和双方信息，交家长处理。
4. **读回确认**：必须实际读回该设备的操作结果，才能从 IndexedDB 删掉。HTTP 200 单独不代表成功，`{ok:false}` 必须按业务失败处理。
5. **WebSocket 仅加速**：收到 `postgres_changes system-ready` 后才视作实时订阅可用；启动、切回前台、网络恢复需主动读取确认，不能只靠推送。
6. **客户端加分等副作用**：现有 `completeHomework` 与 `DemoCore.finish` 会写入积分、成长、奖励等多个字段；本次**未**擅自改变该历史逻辑。后续必须明确这些联动字段的归属/幂等性，不能因为重新合并完成状态再次加分，也不能使旧数据丢失。课程和携带物品不因同步变化产生打卡。

## 旧数据迁移：禁止自动覆盖

原 `local-v1` pending 标记没有记录本机改动时的完整远端基线，无法可靠判断哪些修改早于/晚于云端。因此不能仅比较两个 JSON 后自动选“最后修改时间”或整包覆盖。

正式迁移步骤：各端导出本地备份 → 生产只读记录数据库 revision、备份和可恢复点 → 识别所有设备 pending → 已验证家长认领家庭 → 仅迁移能确认来源的增量操作 → 冲突必须由家长选择 → 家长端/孩子端全部确认 V2 同步 → 最后才撤销旧匿名 RPC。每个关键阶段须可中止、不丢本地记录；从未授权服务端自动迁移真实家庭数据。
