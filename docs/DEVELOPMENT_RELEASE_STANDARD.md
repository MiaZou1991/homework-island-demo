# 开心岛｜开发协作与版本发布规范 V1.2（PR 验收后自动发布）
更新：2026-11-09；适用：所有 ChatGPT 开发/设计对话、GitHub 代码变更与正式发布。

> 核心原则：**独立分支开发、PR 先验收、合并 main 即自动发布。** 无需每次手动点击发布。  
> 状态：主线 PR 检查与自动 Pages 发布由独立工作流执行；**仍需在 GitHub Settings 中启用 main 的必经 PR/检查 Ruleset，才具备真正的技术强制保护**。

## 一、唯一基线
- 仓库：`MiaZou1991/homework-island-demo`；`main` 是唯一正式代码基线。
- 开工前读取 `AGENTS.md`、本文件、`README.md`、相关批准设计和当前代码；记录 `main` SHA。读取失败须明说，不得冒充最新版。
- 权威顺序：**用户最新明确确认的决定 → 已更新到 GitHub 的 AGENTS/批准设计 → main 实际代码 → RELEASE_NOTES/真实部署记录 → 分支与聊天草稿**。出现矛盾先报告，不擅自覆盖。
- 正式代码、交付、版本记录在 GitHub；批准设计同步开心岛项目文件。个人 Library、旧聊天及 localhost 不是正式基线。

## 二、多对话分工与分支
- 需求/设计对话：产出设计、验收标准；不发布。
- 开发对话：**一个任务一个分支、一个 PR**，只修改授权范围，禁止直接推送 `main`；设计预览不进入 main。
- 集成对话：在用户明确批准将 PR 上线后，负责最终验收、合并及记录；**合并进入 main 即自动触发发布**，不另设手动发布审批。
- 功能用 `feat/...`，修复用 `fix/...`，视觉用 `design/...`，维护规范用 `chore/...`；均从最新 `main` 创建。
- 两个对话不得共同维护同一开发分支；碰到同一文件冲突，明确合并先后，后一分支重新同步 `main` 并重测。
- 已有开发分支必须先逐项核对差异和实际状态，不得把旧分支直接作为“最新版”整体覆盖。

## 三、开发红线
- 只有一个家庭、一个孩子；家庭日程可以包含父母等成员筛选，但不是多家庭/多孩子系统。
- 维持确认的“开心岛”最终 Logo、原底部 Tab、批准弹窗稿及视觉素材；不得擅自简化成 emoji/普通卡片。
- 课程与携带物品只提醒不打卡；不得自行增加积分、建设力、奖励结算或改写历史数据。
- 禁止大范围整包覆盖、顺手重构无关功能、测试写入真实家庭数据；同步/权限/存储改动必须单独说明兼容性和回退路径。
- 设计预览和测试使用 `preview=1` 或隔离数据；`127.0.0.1` 仅本机可访问，不能当正式交付链接。

## 四、每个对话必须交付两张卡
开工卡：任务、批准依据、`main` 基线 SHA、自己分支、涉及文件、修改范围、不修改范围、验收点、潜在冲突。

交付卡：任务状态、分支、基线 SHA、提交 SHA、PR、具体改动、保持不变事项、测试命令与真实结果、预览/截图、数据/缓存影响、风险、回退方案、待验收项。

**没有实际部署记录不得宣称“已上线”，只可称“开发完成/待验收/已提交 PR”。**

## 五、合并验收门槛
- PR 只完成一个任务，变更有可读的前后对照、影响范围和已知问题。
- 与最新 `main` 无未解决冲突；主干变更后重新同步、重跑相关测试。
- 业务校验：`node checks/domain.test.cjs`。
- 同步功能涉及的检查：`checks/kaixin-sync.cjs`、`checks/sync-traffic.cjs`、`checks/realtime-signal.cjs`。
- 日程/移动端相关：`checks/family-schedule.cjs`，复核 320 / 375 / 390 / 430 px；必要时实测 iPhone/Safari。
- 静态资源路径、高清图、字体、按钮、Tab 和页面缓存版本需核验；避免 JS/CSS 已更新而 Safari 仍显示旧资源。
- 不能运行的检查必须写清原因和风险，绝不写“已通过”。

## 六、唯一发布流程
1. 开发对话开 PR，完成代码与视觉验收，负责人确认变更范围。
2. PR 的 `domain-sync-and-mobile-qa` 自动检查通过；负责人确认功能、效果和合并上线范围。
3. 集成对话合并 PR 到 `main`；`pages.yml` 由 `push main` 自动触发，按顺序执行领域、同步、手机端及素材构建检查，**全部通过才部署**，无需额外点击发布。发布失败时如实告知，不宣称上线成功。
4. 正式发布记录写入 `RELEASE_NOTES.md` / GitHub Release：版本、PR、部署 SHA、工作流 URL、时间、已验证的线上地址、回退 SHA。
5. 上线后实测关键入口、儿童端、家长端、手机 Safari 缓存及家庭数据兼容。
6. 出故障使用上一健康版本 SHA/Tag 重新部署；数据迁移的回退需单独评估，不能直接删除家庭数据。

**技术实施：** `checks.yml` 负责 PR/main 自动校验，`pages.yml` 恢复 `push main` 自动部署且保留发布前全套检查；`workflow_dispatch` 仅作维护应急入口。**仍需管理员在 Settings 启用 main 的 Ruleset/分支保护**，要求 PR 与 `domain-sync-and-mobile-qa` 必须通过、禁止直接推送及强制推送。该管理配置当前无法经 GitHub 应用写入；未启用前只能靠开发约定避免直接推 main。单人项目不要求第二名审核人，但合并须得到用户对上线的明确确认。

## 八、严格禁止
未经授权推 `main` / 部署；旧版整包覆盖；未验收直接上线；只看 localhost 就宣称手机验证；未记录 SHA 就说最新版；使用真实家庭数据跑破坏性测试；擅改批准设计和业务红线；隐瞒未测试或有冲突。

> 注意：Pages 自动发布将响应任何 `main` 的推送。**仅靠本文规定不能阻止有权限的人绕过 PR**，必须启用 GitHub Ruleset/分支保护，才能真正保证“经过 PR 才能上线”。
